## Task 2 of 9. Database transactions, concurrency and data integrity

### Findings and local changes

- **OTP issuance (medium).** Two workers could both see no outstanding code and try to insert the first row. A single PostgreSQL or SQLite INSERT ON CONFLICT now handles first issuance and replacement. It preserves attempts and expiry during the active window and renews both after expiry. RETURNING refreshes the SQLAlchemy object for callers that reuse a session. Verification rereads a locked row. Signing, purpose binding, attempt caps and single-use consumption continue to apply.
- **Administrator invitations (medium on the development baseline).** Successful verification committed before account creation could fail. The registration caller now consumes the invitation in the same transaction as the account, failure-window cleanup and audit row. Phase 2 already contained this caller correction. Password resets and Phase 2 enrollment use the same deferred-success pattern. A failed attempt remains durable.
- **Donation cooldown (medium).** Closing a request with an older donation date could shorten a donor's cooldown even when each close succeeded legitimately. A single database update increments the donation count and keeps the most recent donation date. The existing conditional request transition prevents a second close from repeating the update.
- **Hospital duplicates (medium).** Concurrent inserts or edits could pass the application precheck. Revision 0014 enforces the same case-insensitive name and branch plus pincode identity, treating missing and empty branches alike. Existing route error handling converts conflicting writes into a conflict response. Hospital references remain protected by the existing foreign key.
- **Unit of work reviewed.** Donor creation, hospital changes, administrative counters and audit events flush under the function-scoped database dependency. It commits before success is sent or background notifications run. The session rolls back on database and HTTP failures. Approve, decline, expire and close use conditional SQL updates. Close locks donor rows in stable order and privacy review locks the donor before rechecking the receipt. Phase 2 refresh rotation and concurrent administrative privilege changes use their existing locks and revocation checks.
- **Retry boundaries.** Concurrent transitions on the same request have a single winner. A new public blood request generates a new identity on each submission. Two intentional requests can have identical payloads, so deduplication based on patient attributes would lose valid requests. Clients retrying after an ambiguous create response have no idempotency key today. SMTP delivery after a committed operation remains an external side effect; delivery retries and durable dispatch belong to Task 5. Each resend replaces the current OTP and only the latest committed code is valid.
