# LifeConnect database and certificate recovery

## Recovery point and responsibilities

A recovery point pairs a PostgreSQL custom-format dump with the completed files in the API and scheduler's shared `generated_certificates` volume (`/code/app/static/images/certificates`). The database contains donor and administrator records, blood requests, certificate ownership and delivery audit records, and pending erasures. Copying the database and certificate volume at different times can resurrect erased files or lose newly issued certificates. A live copy of the PostgreSQL data directory is unsuitable for this procedure.

**Proposed objectives for operator approval.** Take a paired backup at least daily, and before risky migrations. A 24-hour RPO depends on at least one successful, recoverable off-site copy every 24 hours. Page the backup owner when that window is missed. A proposed 4-hour RTO covers retrieval, provisioning, restoration, privacy reconciliation, checks and controlled cutover. Neither objective is measured at production scale. Record timings and sizes at a representative quarterly drill and following storage or major-version changes. If the write pause or data-loss window is unacceptable, choose a coordinated snapshot and PostgreSQL WAL/PITR design before adopting this procedure.

The data owner must approve retention, legal holds, erasure-register ownership and location. The existing proposal is 30 days. Keep its lifecycle consistent across object versions and replicas. There is no automatic backup deletion in this tool. See [Data retention](DATA_RETENTION.md). The platform owner operates backups and monitors failures. A separate recovery operator controls restores and the custodian controls decryption. Record timestamp, release, revision, archive identifier, verification outcome and timings in restricted operations records. Keep row values, certificate names, passwords and connection strings out of tickets and logs.

## Prepare the storage and tools

- Use trusted Python 3.11+ and PostgreSQL clients (`psql`, `pg_dump`, `pg_restore`, `createdb`) on PATH. Match source and target server major versions and use the corresponding client major version for routine recovery. Compose specifies PostgreSQL 16. Provision the destination with the same encoding, locale provider, collation and required extensions.
- Use an encrypted, access-controlled staging filesystem for all work. The utility writes plaintext **inside** that filesystem. On Windows provision restrictive ACLs before creating any directories. On Unix the utility requests a private directory and file creation mask. Protect scratch space and the actual recovery database volume as well.
- Store completed bundles on encrypted storage in a separate failure domain and account, using authenticated transport, versioning and retention locks compatible with approved erasures. Restrict the backup identity to creating objects. Separate read/decrypt, restore and retention-management permissions. Record an independently authenticated digest or signed inventory in the trusted catalog. The bundle's internal SHA-256 hashes detect corruption; a party able to change the entire bundle could also change its manifest. Test key recovery with the custodian.
- Prepare PostgreSQL roles and grants, host configuration, application release, deployment manifests, TLS certificates and secrets through their own restricted recovery channels. A database dump omits cluster roles and server configuration. Restore intentionally omits original object ownership, grants and tablespace placement. Use a dedicated restore owner and reapply the reviewed runtime and migration grants before application startup.
- Redis contains expiring rate-limit counters. Its persistent volume is outside the database/certificate bundle. Never substitute process-local throttling during recovery. Keep sensitive routes closed until the shared store is healthy and any lost counter windows have elapsed, or use an approved recovery of the same Redis state. Keep the erasure register independent of the bundle.

## Create a recovery point

1. Obtain a maintenance window. Block incoming writes, drain requests and background email/certificate tasks, and stop all API replicas, scheduler jobs, migration processes, and other database or certificate writers. Verify quiet database clients and quiescent volume activity. Keep PostgreSQL available. The CLI confirmation records the operator's assertion. It cannot stop independent writers.
2. Mount the **actual** certificate volume read-only and verify its identity against the deployment. An empty mount is legitimate only after the operator confirms that no certificates should be present. Use an explicit database account able to dump every application table and sequence. Set `PGHOST`, `PGPORT`, `PGUSER` and a restricted `PGPASSFILE` in this shell. For remote access configure `PGSSLMODE=verify-full` and a trusted CA. Do not place credentials in arguments. Use a clean libpq environment without unrelated service, database or session overrides.
3. From the repository root, choose a **new** directory under an existing encrypted parent. Substitute approved paths and the source database name.

   ```sh
   python scripts/recovery_bundle.py backup --database lifeconnect --certificates /mnt/lc-certificates --output /secure-staging/point-001 --writers-stopped
   ```

4. Require exit zero and the manifest. Release the maintenance window after the paired capture is complete. Transfer the entire bundle while preserving exact file names and modification timestamps, including subsecond precision. A metadata-preserving archive on a supported encrypted filesystem is suitable. Restoring the wrong timestamps can prematurely expire a certificate. Verify the transferred artifact against the independent catalog and rehearse the restore. Mark failed or incomplete attempts unusable. Retry with a fresh output directory. Avoid publishing or combining portions of two attempts.

## Restore, verify and roll back

1. Authenticate the backup against the independent catalog and decrypt it into private storage using the custodian's procedure. Treat dumps as executable SQL from a trusted producer. Provision a separately network-isolated recovery PostgreSQL cluster with no application connections, email egress, scheduler or production routes. Point `PGHOST`, `PGPORT`, `PGUSER` and `PGPASSFILE` at that cluster. Verify server identity independently. The recovery role needs database creation permission there. Choose a new private output directory.

   ```sh
   python scripts/recovery_bundle.py restore --bundle /secure-staging/point-001 --output /secure-recovery/drill-001 --isolated-cluster
   ```

2. Record the generated `lc_recovery_...` database name. The tool verifies input hashes, copies and verifies certificate bytes and timestamps, creates a fresh database from template0, checks locale defaults, restores in one transaction, and compares the Alembic revision. It does not replace a database or use PostgreSQL's clean/drop option. The restored certificate directory is under the new output directory. A failed attempt can leave private files and an empty or unapproved new database. Quarantine that pair, preserve diagnostic evidence, and retry into fresh destinations.
3. With outbound services still disabled, compare donor, admin, request and audit counts with trusted recovery-point records. Check joined request/hospital/response counts, donor-linked audit records and pending erasure rows. Confirm constraints are present and valid. Spot-check authorized certificate bytes against the private manifest copy. Some accepted or expired certificates are intentionally absent. Reconcile unexpected omissions and orphan files before cutover. Run the application revision paired with the dump; perform any later schema upgrade separately.
4. Replay and verify **approved** erasures made after the backup using the restricted register. Keep pending removals hidden and verify physical file cleanup. Revoke restored refresh sessions and invalidate pre-recovery access tokens and OTPs under the authorized security procedure. Reconcile post-backup account deactivations and administrator privilege changes. Reconcile uncertain certificate/mail deliveries with relay records before sending anything again.
5. Reapply least-privilege grants, provision the shared Redis and application configuration, and set the correct owner and permissions on the restored certificate volume. Exercise authenticated donor/admin reads, a matching blood-request join, a private certificate download and denied unauthorized access with synthetic identities. Keep scheduler and real SMTP disabled during verification. Record actual RPO/RTO and obtain sign-off before any traffic change.
6. **Rollback.** Before cutover, leave the original database and volume in place and keep serving from the approved pair, or remain in maintenance if it is unsafe. If the target has accepted writes, freeze access again and reconcile those writes and erasures before reverting. Always switch the database and certificate volume together. Release quarantined artifacts only through the authorized retention process.

## Repeat the isolated drill

Run `python -m pytest -q tests/test_recovery_bundle.py` in the project test environment with PostgreSQL client and server binaries on PATH. The integration test initializes two temporary password-authenticated loopback clusters, migrates the source, seeds synthetic workflows, restores into the other cluster, and checks relational links, a foreign-key rejection, certificate bytes, timestamps, the erasure queue, and refusal of an existing destination or altered backup. It never needs a production connection.
